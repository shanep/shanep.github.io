## Background

![Where the stack runs: curl and QEMU user networking on your machine, and the layers you write inside the unikernel](./g-stack.svg)

QEMU, the Quick Emulator, gives your kernel a virtio-net card, which is a network card
designed for virtual machines. There are no registers to send a packet through. You and the
card share rings of descriptors in memory: you write the address of a buffer into a ring and
tell the card, and the card reads or writes that memory directly. That direct access is what
every real network card does, so this driver works much the way a real one does.

The card speaks the legacy interface, because `make run` starts it with `disable-modern=on`.
Its registers are I/O ports at the address in `dev.bar0`, and they are laid out in the
[virtio specification](https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html). The
parts you want are the Legacy Interface notes on virtqueues in section 2, the Legacy Interfaces
note on Peripheral Component Interconnect (PCI) device layout in section 4.1 for the registers,
and section 5.1 for the network device.

QEMU's user networking is what the kernel is plugged into, and it is not a real network. It
puts your kernel at `10.0.2.15` with the gateway at `10.0.2.2` and a Domain Name System (DNS)
server at `10.0.2.3`, and it answers Address Resolution Protocol (ARP) requests itself. It
also ends Transmission Control Protocol (TCP) itself, so when you `curl` your kernel, `curl`
talks to your machine's TCP, and that talks to QEMU, and QEMU talks to you. Your stack never
sees a segment from Linux this way, only one from QEMU's own TCP.

Every frame goes to `build/packets.pcap` too, so you can open it in Wireshark and check your
work the same way you did in P4.

## Task 1 - The driver

Implement everything in `src/kernel/virtio_net.h`. The `virtio_net_t` struct is yours.

`virtio_net_init()` follows the steps in the specification: call `pci_enable()`, reset the
card, set the acknowledge and driver status bits, read the feature bits and accept the ones
you need, set up the two rings, offer your receive buffers, and set the driver OK bit. Queue
0 is receive and queue 1 is transmit.

Each buffer starts with a 10 byte network header, which you leave zeroed when you send and
skip when you receive. The rings go in static memory, and since there is no paging, a pointer
is a physical address, which is what the card wants. Use `barrier()` between filling in a
descriptor and telling the card about it, or the compiler can reorder those writes.

::: warning

A legacy device picks the ring size, and you do not get a vote. Read the size from the card
and use that, since it changes between QEMU builds: the one in Homebrew offers 256 entries and
the one in Debian offers 1024. A driver with a fixed ring of 256 boots on one machine and
sits silently on another. Make room for 1024, which is the most QEMU allows.

:::

The card can only be tested on the card, so `src/kernel` is not in your coverage report. There
is no debugger here, so `kputs()`, `kputu()` and `kputx()` on the serial console are your
friends. If you see nothing at all, open `build/packets.pcap` to find out whether your frames
are getting out.

## Task 2 - No C library

`make kernel` links with no C library and no `libgcc`, and this is the first time your stack
has been held to that. If you divided a 64 bit number anywhere in your stack, on a 32 bit
target that is a call to a function that does not exist.

```text
undefined reference to `__udivdi3'
```

Use 32 bit math. `memcpy`, `memmove`, `memset`, `memcmp` and `strlen` from `src/stack/port.h`
are all you can count on. Your stack also builds at both widths now, so `size_t` is not always
64 bits. Make sure a `-Wconversion` warning is fixed and not cast away.

Once your driver works, your kernel gets this far.

```text
hello from the unikernel
stack up at 10.0.2.15
ping gateway: ok
dns example.com: 104.20.23.154
```

If that prints, your driver, Ethernet, ARP, Internet Protocol (IP), Internet Control Message
Protocol (ICMP), User Datagram Protocol (UDP) and DNS all work on a machine with no operating
system on it. That is worth stopping to enjoy for a minute.

## Task 3 - The web server

Implement everything in `src/stack/http.h`. This is a small Hypertext Transfer Protocol (HTTP)
1.1 server that answers one request per connection and then closes, so there is no keep-alive
to think about. The `http_t` struct is yours.

| Request | Answer |
| ------- | ------ |
| `GET /` | `200` and a page with `Hello from the unikernel` in it |
| `GET /bytes/N` | `200` and `N` bytes of `http_pattern()` |
| `POST /count` | `200` and `length=<bytes> fnv1a=<hash>\n` for the body |
| Anything else with `GET` | `404` |
| Any other method | `405` |
| A request line and headers over `HTTP_MAX_HEADER` | `431` |

Every answer has a `Content-Length` and a `Connection: close`. `http_pattern()` must return
exactly this, because the test computes the same bytes on the other side.

```c
return (uint8_t)((offset * 31U + (offset >> 8)) & 0xFFU);
```

The hash is 32 bit FNV-1a, named for Fowler, Noll and Vo. Start at `2166136261`, and for each
byte, XOR it in and multiply by `16777619`.

`http_poll()` must never block, and that is where the design work is. A 5 MB response does not
fit in a 64 KB send buffer, so you write what fits and pick up where you left off on the next
call. Do not build the whole response in memory, since you have no memory to build it in.
Compute the pattern a chunk at a time. A request can also arrive split across any number of
segments, so keep reading until you have seen the blank line.

Test all of this over the simulator first, using the two stack setup in `tests/smoke-test.c`.
It is a lot easier to debug in a Linux process.

## Task 4 - The boot test

```bash
make boot-test
```

This boots your kernel and tests it from the outside with `curl`, so it can not be fooled.

```text
hello from the unikernel
stack up at 10.0.2.15
ping gateway: ok
dns example.com: 104.20.23.154
http listening on port 80
ok: GET / returns the page
ok: a missing page is a 404
ok: a bad method is a 405
ok: GET /bytes/5000000 is identical
ok: POST /count hashes the upload
ok: 30 requests in a row
boot test passed, and the packets are in build/packets.pcap
```

Your DNS line will likely show a different address, since `example.com` moves around. Run
`make run` in one terminal and try it by hand from another.

```bash
curl -v http://127.0.0.1:8080/
```

Then add the boot test to your continuous integration (CI). Add these two lines to the end of
`.github/workflows/ci.yml`, at the same indent as the other steps.

```yaml
    - name: make boot-test
      run: make boot-test
```

## Instructor Notes

Instructor note, not shown to students.

**Run the boot test on the student's repository, on both QEMU builds if you can.** The ring size
bug only shows up on one of them. A student who tested on one machine can pass there and
hang on the other. I hit this myself: Homebrew's 10.2.1 offers at most 256 and Debian's 10.0.13
offers 1024.

**The DNS and ping lines do not stop the boot.** They only print `no answer`, so a machine with
no way out to the Internet still serves pages. The boot test does not fail on them, so rubric row
2 is a read of the transcript.

**`curl` through `hostfwd` proves the stack talks to libslirp, not to Linux.** The options Linux
offers only show up in the golden tests and in `scripts/live-interop.sh`, which runs real Linux
TCP against the kernel over a tap device with `netem`. Against the solution, that moved a 2 MB
download intact at 25.4 MB per second, the same 2 MB upload with the right hash, and 20 requests
in a row, with 40 of 2633 segments dropped. Docker Desktop's kernel has no `ifb`, so on a Mac it
only loses what Linux sends. Loss of what the guest sends is covered by the simulator.

**The initial sequence number is not secure.** `boot_entropy()` in `src/kernel/main.c` hashes the
time stamp counter, so it differs on every boot and a person who can see the time can guess it.
[RFC 9293](https://www.rfc-editor.org/rfc/rfc9293) asks for better. This is fine for a kernel
behind QEMU's user networking, and it is a good thing to ask about in a final conversation.

**Measured size.** 497 lines: `virtio_net.c` 153, `virtio_net.h` 38, `http.c` 292 and `http.h` 14.
15 hours is an estimate, and this is the one I would watch the most, since the driver has no unit
tests and a failure is often silence.
