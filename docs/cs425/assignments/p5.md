# P5 - Build Your Own Dev Box

**Week 3 · 50 points · about 4 hours · submit in Canvas**

## Overview

Codespaces hands you a working machine. Somebody wrote a container definition, and
a build system you never saw provisioned a Linux box, installed a compiler, and
opened an editor onto it. In this project you do that job yourself, by hand, on
`onyx.boisestate.edu`, over SSH.

There is a reason this belongs in a networking class. Everything you are about to
do is a network operation. Logging in is a TCP connection to port 22. Your shell
dies when that connection dies. `git clone` is another connection, to another host,
that has to authenticate itself. The build output you are watching scroll past is
being carried back to you a packet at a time. By the end you will have a one command
edit-here, build-there loop, and you will know which parts of it are on the wire.

::: tip

P5 is the fifth project by number only. It is due in **week 3**, before P1, because
every project after it assumes you have a working Onyx account and can get your code
onto it. Do it early.

:::

Create your repository from the
[starter](https://github.com/shanep/makefile-project-starter) using the
**Use this template** button and name your copy `cs425-p5`. You will not write any C
in this project, but the template gives you a repository whose CI and submission
report already work, and a real project to build on Onyx in Task 6.

## Ground rules

Onyx is a **shared** machine. Several hundred students have accounts on it and a
few dozen are usually logged in at once. Nothing you do in this project may
interfere with them:

- Do not run long, heavy builds in a loop.
- Do not bind a listening socket to `0.0.0.0`. Bind to `127.0.0.1` and reach it
  through a tunnel, as in Task 8.
- Kill anything you start. A stray process holding a port is somebody else's bug
  report next week.

::: danger

You are a guest on a production system owned by the department. Scanning it,
probing other users' processes, or trying to read files that are not yours is an
academic integrity violation and a violation of the university acceptable use
policy. The point of this project is to configure **your own** account well.

:::

## Task 1 - First login and a survey of the machine

Log in with your Boise State credentials:

```bash
ssh <username>@onyx.boisestate.edu
```

Record the answers to the following in your report. Say which command produced
each one.

- What distribution and kernel version is Onyx running? (`uname -a`, `/etc/os-release`)
- How many CPUs and how much memory does it have? (`nproc`, `free -h`)
- How much disk space do you have in your home directory, and is there a quota?
- How many other users are logged in right now? (`who`)

## Task 2 - Key based login

Typing your password into every SSH connection is going to make the rest of this
project miserable, and it is not how anyone works. Generate a key pair on **your
laptop**, not on Onyx:

```bash
ssh-keygen -t ed25519 -C "you@boisestate.edu"
```

Install the public half on Onyx. On macOS or Linux, `ssh-copy-id` does it:

```bash
ssh-copy-id <username>@onyx.boisestate.edu
```

If `ssh-copy-id` is not available, append the contents of `~/.ssh/id_ed25519.pub`
to `~/.ssh/authorized_keys` on Onyx yourself. SSH refuses to use the file if the
permissions are loose, so on Onyx:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

Verify that `ssh <username>@onyx.boisestate.edu` no longer asks for a password.

In your report, answer in two or three sentences: your private key never leaves
your laptop, so what exactly does the server check, and why is this stronger than
sending a password over the connection?

## Task 3 - An SSH config with connection reuse

Nobody types the full host name every time. Create `~/.ssh/config` on your laptop:

```
Host onyx
    HostName onyx.boisestate.edu
    User <username>
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 60
    ControlMaster auto
    ControlPath ~/.ssh/cm-%r@%h:%p
    ControlPersist 10m
```

`chmod 600 ~/.ssh/config` and confirm that `ssh onyx uname -n` works.

The last three settings turn on connection multiplexing: the first connection stays
open, and later connections to the same host reuse it instead of paying for a new
TCP handshake and a new key exchange. Measure it. With no connection open, run:

```bash
ssh -O exit onyx 2>/dev/null   # tear down any existing master
time ssh onyx true             # first connection: full setup
time ssh onyx true             # reused connection
```

Put both timings in your report and explain the difference in terms of what has to
happen on the wire in each case.

## Task 4 - Map the path to the box

You have been reading about delay, routing, and DNS in chapter 1. Onyx is a real
host on a real network, so measure it.

From your laptop:

```bash
dig onyx.boisestate.edu          # or: nslookup onyx.boisestate.edu
traceroute onyx.boisestate.edu   # Windows: tracert
ping -c 5 onyx.boisestate.edu
```

On Onyx:

```bash
ip addr
ip route
cat /etc/resolv.conf
```

Report:

1. What IP address does `onyx.boisestate.edu` resolve to, and what is the TTL on
   that record?
2. Is that address public, or private per RFC 1918? How do you know?
3. How many hops are between you and Onyx from where you are working? Does the
   count change if you move to campus wifi or off VPN? Explain what a hop is.
4. What is your average round trip time, and roughly how much of it can propagation
   delay account for? Boise State is about 25 km from downtown Boise, and light in
   fiber moves at roughly 2 x 10^8 m/s. Show the arithmetic.
5. What is the MTU on Onyx's primary interface, and what are its DNS resolvers?

## Task 5 - Build the toolchain by hand

Codespaces installed your tools from a container definition. Here you check what is
present and fill in what is missing, into your own home directory. You do not have
root on Onyx and you are not getting it.

Record the version of each of these on **both** Codespaces and Onyx:

`gcc`, `make`, `git`, `gdb`, `valgrind`, `gcovr`, `python3`

Anything missing goes into `~/.local`. `gcovr`, for instance, installs with
`pip3 install --user gcovr`, which puts it in `~/.local/bin`. Add that directory
to your `PATH` in `~/.bashrc` and confirm it survives a fresh login.

Now the gotcha that will cost you an hour later if you skip it. Run these two
commands from your laptop and compare:

```bash
ssh onyx 'echo $PATH'
ssh onyx -t 'echo $PATH'
```

A non-interactive `ssh host command` does not source the same startup files an
interactive login does, so `~/.local/bin` may be missing from `PATH` in exactly the
case your script in Task 7 depends on. Explain in your report which startup file is
read in which case, and say how you fixed it.

In your report, list every version that differs between Codespaces and Onyx. The
compiler difference is the whole reason this course requires two machines.

## Task 6 - Get your code onto the box and build it

Onyx has to be able to authenticate to GitHub. Choose one and say which you chose
and why:

- Generate a **second** key pair on Onyx and add the public half to your GitHub
  account. The private key lives on a shared machine, which is a real tradeoff.
- Forward your laptop's agent with `ssh -A onyx`. Nothing is stored on Onyx, but
  while you are connected, anyone with root on that machine can use your agent.

Clone your `cs425-p0` repository onto Onyx and build it there:

```bash
make clean
make all
make check
```

Include the output in your report. If P0 built in Codespaces but not here, fix it.
That is the portability rule from the grading rubric, and this is the moment you
find out.

## Task 7 - Implement `devbox.sh`

This is the heart of the project. Write a shell script, `devbox.sh`, in the root of
your `cs425-p5` repository, that gives you an edit-on-your-laptop, build-on-Onyx
loop in one command.

It must support exactly these subcommands:

| Command | Behavior |
| ------- | -------- |
| `./devbox.sh sync` | Copy the working tree to `~/cs425/<project>` on Onyx |
| `./devbox.sh run "<cmd>"` | Run `<cmd>` in the remote project directory, streaming output |
| `./devbox.sh check` | `sync`, then run `make clean && make all && make check` remotely |
| `./devbox.sh shell` | Open an interactive shell in the remote project directory |
| `./devbox.sh -h` | Print usage and exit 0 |

Requirements:

- Use `rsync` for `sync`, and exclude `build/` and `.git/`. Copying build artifacts
  from a Mac to a Linux box is how you get a link error that makes no sense.
- **The remote exit status is the script's exit status.** If `make check` fails on
  Onyx, `./devbox.sh check` must exit non-zero. A wrapper that always exits 0 is
  worse than no wrapper, because you will trust it.
- No hard coded user name. Take the host from an `ONYX_HOST` environment variable
  and default it to the `onyx` alias you configured in Task 3.
- Start with `set -eu`, quote your variables, and run it through
  [shellcheck](https://www.shellcheck.net/) until it is clean.
- It must work from both macOS and Linux. `readlink -f` and `sed -i` do not mean
  the same thing on both, so avoid them or handle both.
- It must reuse the multiplexed connection from Task 3, so `check` does not pay for
  a fresh handshake on every command.

Demonstrate it in your report: a passing `./devbox.sh check`, a failing one (break
a test on purpose), and the shell exit status of each, shown with `echo $?`.

## Task 8 - A port of your own, and a tunnel to it

Every project from P1 on binds a socket. On a shared machine two students who pick
port 8080 collide, and the second one gets `EADDRINUSE` with no idea why.

Pick your port with `echo $((10000 + $(id -u) % 20000))` on Onyx. Confirm nothing
is listening on it with `ss -ltn`. Then start something trivial that binds it to
loopback only:

```bash
python3 -m http.server "$PORT" --bind 127.0.0.1
```

That server is not reachable from the outside world, which is the point. From your
laptop, forward it:

```bash
ssh -N -L "$PORT:127.0.0.1:$PORT" onyx
```

Open `http://localhost:$PORT` in your browser and screenshot the directory listing.
Then stop the tunnel and kill the server.

In your report, describe what the tunnel is doing: which process opens which
connection, where the payload is encrypted, and at which layer the forwarding
happens. Then explain why binding to `127.0.0.1` rather than `0.0.0.0` was the
right call on a shared machine.

## Task 9 - Survive a disconnect

Your remote shell is a child of the SSH connection. When the TCP connection breaks,
because your laptop sleeps or the wifi drops, that shell and everything it is running
gets a `SIGHUP` and dies. A ten minute build dies with it.

```bash
tmux new -s cs425      # start a named session
# start something long, then detach with Ctrl-b d
ssh onyx
tmux attach -t cs425   # it is still running
```

Do this with something that runs long enough to prove the point, disconnect on
purpose (close the terminal, do not just detach), reconnect, and reattach. Say in
your report what tmux changes about the process tree such that the work survives.
