Q3. Nothing was listening on port 33434, so XMission's server answered the UDP datagram with ICMP port unreachable (type 3, code 3). Onyx's kernel matched the ICMP message to the socket (the ICMP payload carries the original IP header and the first 8 bytes of the UDP header, so the ports are in it) and reported it on the next call as ECONNREFUSED. That only works because the socket is connect()ed. 127.0.0.1 gives the same error, from Onyx itself. This is how tracepath printed reached in A4.

Q4. Hop 2, or something right behind it. Hop 3 answers UDP and TCP probes every time, and answers a direct ping, so it would almost certainly have answered a TTL-expired echo request too if one had reached it. None did, so echo requests headed off campus are dropped at hop 2. Hop 2's address is 10.1.2.53, an RFC 1918 private address: a box inside campus that is not meant to be reached from outside. Probably the campus firewall, but that is not confirmed, so say "probably".
Q5. Forwarding and answering are different jobs. Forwarding is the data plane, done in hardware for every packet. Making an ICMP time exceeded message is work for the router's own CPU, the control plane, and routers rate limit it, deprioritize it, or turn it off. A hop that loses 100% of the probes is a router that does not talk back, not one that drops your traffic. Loss only matters if it carries through to the last hop.
If it happens live  In one rehearsal the gateway took 1,032 ms to answer one TCP probe while hop 3 behind it answered in 0.7 ms. A router behind it cannot be faster at forwarding; the gateway was just slow to write the ICMP message. Same lesson as Q5.

Exit question

Any two of: the gateway answers ping, so ICMP works locally; curl to Google returned 200; UDP and TCP traces reached Salt Lake City; XMission's server answered round 3 with port unreachable; the ICMP trace dies at a private address inside campus, so the drop is local policy, not a dead Internet.
